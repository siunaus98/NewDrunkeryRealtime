# 文本与场景修改硬约束

本文档用于记录后续开发中必须长期遵守的文本 / 编码 / 场景修改约束，目的不是“写得更漂亮”，而是避免再次出现：

- 中文乱码反复回流
- `.gd` / `.tscn` 中的字符串字面量被污染
- 场景文本被截断
- 运行时看似正常，但源文件已经处于高风险状态

项目路径：
`D:\NP\NewDrunkeryRealtime\NewDrunkeryRealtime`

## 1. 适用范围

以下情况默认都适用本约束：

- 修改任何玩家可见中文文本
- 修改 `.gd` 中的中文字符串
- 修改 `.tscn` 中的 `text`、`display_name`、导出默认值等文本字段
- 修改依赖固定节点路径的 UI 模板场景

## 2. 硬约束

### 2.1 不在已污染文本上做脆弱局部替换

- 如果某段中文已经出现明显 mojibake、引号异常、字面量断裂或文本块结构不可信，默认不要继续做局部替换。
- 这类情况优先整段、整节、整文件重写。
- 原因很直接：局部补丁容易留下半坏状态，后续会继续回流。

### 2.2 修改中文时同时检查“源文件状态”，不是只看运行结果

- 不能因为游戏里暂时看起来正常，就默认源文件没有问题。
- 每次改中文后，都要检查文件实际内容是否完整、是否仍为正确中文、是否存在损坏字面量。
- 特别注意 `.tscn` 这种既是配置文本、又直接决定节点结构的文件。

### 2.3 玩家可见文本和导出默认值要一起检查

- 不只检查运行时会被覆盖的 label 文本。
- 同时检查：
  - `@export` 默认字符串
  - 场景实例上的 `display_name`
  - `text = "..."`
  - 调试提示、结算提示、商店提示、状态说明
- 因为很多乱码不会立刻在当前流程暴露，但会在后续编辑场景、改实例、切状态时重新出现。

### 2.4 改 `.tscn` 后必须警惕节点结构损坏

- 修改主场景或 UI 模板场景时，不能只关注文案。
- 必须同时确认：
  - 节点树没有被截断
  - 节点路径仍与脚本中的 `@onready` / `get_node()` 一致
  - 模板节点仍完整存在
- 尤其是 `OrderHud` 这类依赖固定子路径的模板树，任何缺节点都可能变成运行时错误。

### 2.5 文本修复优先与功能修复分轮处理

- 默认先确认功能链路，再集中处理中文显示、乱码和文本统一。
- 不在同一轮里频繁来回混改“功能行为”和“文本污染”，除非问题本身已经影响场景结构或运行。
- 这样做是为了减少噪音，避免把功能回归和编码问题搅在一起。

### 2.6 每轮文本 / 场景改动后至少做一次 Godot 冒烟验证

默认最少执行：

- `--headless --quit`
- `--headless --import --quit`

目的：

- 尽早发现 `.gd` 语法损坏
- 尽早发现 `.tscn` 解析失败
- 尽早发现 import 或资源引用层面的连带问题

### 2.7 发现中文再次异常时，优先按“源文件污染”排查

- 不要先把它当普通错字。
- 默认排查顺序应为：
  1. 源文件文本是否已被污染
  2. 场景实例文本和脚本默认值是否不一致
  3. 最近一次改动是否造成局部坏文本回流
  4. 如果源文件文本正常但运行时显示为方框或乱码，排查控件字体回退、主题字体继承、按钮多行文本渲染等显示层问题
  5. 是否需要直接整段 / 整文件重写

### 2.8 中文 UI 尽量避免依赖 Button.text 承载多行信息

- 多行中文说明优先使用 `Label` / `RichTextLabel`，按钮只承担点击区域。
- 如果需要卡片式按钮，优先使用 `Button` 内嵌 `MarginContainer` + `Label` 的结构。
- 后续中文 UI 继续增多时，建议引入项目内置中文字体并建立全局 Theme，避免长期依赖系统字体回退。

## 4. 一句话执行原则

后续再遇到中文问题时，默认按下面这句话执行：

`先把它当“源文件污染或场景结构风险”处理，而不是先当普通文案错字处理。`
