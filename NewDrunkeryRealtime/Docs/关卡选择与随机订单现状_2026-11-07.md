# 关卡选择与随机订单现状

## 本轮修复

关卡选择原先把全部卡片横排，第二、三天各5个方案超出屏幕。共享卡片区现置于滚动容器中，左右键自动保证所选卡片可见，首尾循环同步滚动；鼠标滚轮和底部滚动条可查看其余方案。按需扩充卡片池，不再硬性限于5个。切换菜单/祝福等界面重置滚动，容器显隐跟随卡片区。

验证：`tools/validate_order_group_scrolling.gd` 覆盖实际第二天5方案、键盘追随、首尾循环、滚轮、8方案及返回菜单；OpenGL截图为 `_artifact_work/order_group_last_option.png`。

## 同一天不同方案的实际区别

正式流程从天数对应模板取候选，再在确认时调用 `OrderGroupDefs.build_group_for_menu()` 重建菜品订单。

| 内容 | 处理方式 |
| --- | --- |
| 波次数、每波顾客槽数、目标窗口 | 保留模板结构；窗口还受已解锁上菜口映射限制 |
| 波间休息时间 | 保留模板值，如第二天为4.5至5.5秒 |
| 普通敌人类型池 | 保留模板，按战斗区归属筛选；池内没有对应区域类型时有保底类型 |
| 波次敌人数 | 会按重建后的订单条目数和波次计算，精英多菜也会影响 |
| 客人具体菜品 | 替换为当前菜单的加权抽取，不保留模板原菜品主题 |
| 食材产出池 | 按当前菜单所需重新计算，覆盖模板原食材池；排除BOSS专属食材 |
| 精英概率 | 第三天起统一30%，还须菜单具有可组成的酒水与菜品类别；不同方案无独立概率 |
| 耐心、经验、金币 | 根据抽中的菜品统一计算，不使用模板原耐心值，无方案专属倍率 |
| 地图机制与BOSS | 依据整局天数进度配置，不由同一天选择的方案改变 |

例如第二天前两方案各4个顾客槽，后三方案各5个；皆2波。各方案敌人池和休息时间不同，但不会保证“甜味绿洲”多点甜品、“商队考核”多点高级菜。甜品目前是额外招待，不进入普通点单池。旧标题、说明仍有此类过时主题描述，本轮未重设方案规则。

第一天正式只开放第一个模板。第四天及以后没有独立模板，会复用第三天5个方案，并在实际生成时覆盖成当前天数；因此卡片标题可能仍写第三日，但其精英等天数规则按实际天数计算。

## 随机种子的真实状态

目前不是所有随机都由同一个整局种子驱动。生成函数支持显式 `random_seed`，但正式 `LevelFlowController` 未传入，确认关卡时会对新随机数生成器 `randomize()`。显式种子可复现菜品选择和精英组合；配方熟成度仍在 `TestItemDefs.instantiate_order_recipe_for_dish()` 中使用全局 `pick_random()`，因此单独传入该种子也不能完整复现订单熟成度。

后续若要实现同局种子完全复现，应独立接入整局种子、日期与关卡ID派生的订单随机流，并把熟成度抽取纳入同一流；这不属于本轮列表修复。
