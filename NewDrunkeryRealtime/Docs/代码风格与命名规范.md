# 代码风格与命名规范

本文档记录 NewDrunkeryRealtime 项目当前**实际在用**的 GDScript 代码约定，基于对现有代码库的分析整理，目的是让后续新写的代码和已有代码保持一致，而不是引入一套“理论上更好”但和现状脱节的规范。如果某条约定在现有代码里不是100%严格执行，会特别标注出来。

## 1. 命名

### 类名 / class_name

- 只有被当作“静态工具类/数据类”跨脚本引用的类才声明 `class_name`，例如 `LevelRefs`、`RunProgressionState`、`LevelContext`、`BlessingDefs`、`OrderGroupDefs`、`TestItemDefs`。
- 大多数脚本（尤其是挂在节点上的行为脚本，如 `Main.gd`、`BasicEnemy.gd`、`BattleManager.gd`、`OrderManager.gd`）**不声明** `class_name`，而是在需要引用的脚本顶部用 `preload` 建立别名：

```gdscript
const LevelRefs = preload("res://Scripts/Core/LevelRefs.gd")
const PlayerCombatController = preload("res://Scripts/Player/PlayerCombatController.gd")
```

新写脚本时按这个规则判断：这个类会不会被其他脚本当类型/静态方法调用？会的话考虑加 `class_name`；只是挂在某个具体节点上做行为逻辑的，不用加，用 `preload` 常量引用即可。

### 文件名

全部 PascalCase，和类名/概念名一一对应，例如 `PlayerCombatController.gd`、`BulletHellEnemy.gd`。`preload` 常量名与文件名（去掉 `.gd`）保持一致。

### 变量

- 一般变量、成员变量：snake_case，例如 `move_speed_base`、`attack_cooldown_remaining`。
- 方法：snake_case，公开方法不加前缀，私有/内部辅助方法加 `_` 前缀，例如 `_update_health_label()`、`_apply_attack_hit()`、`_resolve_scene_nodes()`。**这条对方法执行得很严格**，新代码要保持。
- 字段的 `_` 私有前缀**不强制**——项目里大量内部状态字段（如 `current_health`、`attack_cooldown_remaining`）并未加下划线，只有少数字段（如 `Main.gd` 的 `_toggle_orders_last_frame`）加了。跟随现有文件里同类变量的写法，不用刻意统一改造。
- 常量：SCREAMING_SNAKE_CASE，ID 类常量优先用 `StringName`（`&"xxx"`）而不是普通 `String`：

```gdscript
const MEAT_RED_ID: StringName = &"meat_red"
const PROCESS_STATE_CUT: StringName = &"cut"
```

### 信号

信号名是“事件已发生”的状态化描述，不是祈使动词，也不加 `on_` 前缀（`on_` 留给处理函数）：

```gdscript
signal defeated(enemy: Node2D, ...)
signal orders_changed(order_list: Array)
signal order_completed(...)
signal level_up_reached(new_level: int)
```

处理函数统一 `_on_<signal_name>` 格式：`_on_order_completed`、`_on_enemy_defeated`。

连接信号前先判断是否已连接，避免重复连接（项目里的固定写法）：

```gdscript
if target.has_signal("order_completed") and not target.is_connected("order_completed", callable):
    target.connect("order_completed", callable)
```

### @onready 节点变量

严格类型标注，变量名是节点角色的语义化 snake_case，不是直接照抄节点名大小写：

```gdscript
@onready var sprite: Sprite2D = $Sprite2D
@onready var collision_shape: CollisionShape2D = $CollisionShape2D
@onready var item_push_area: Area2D = $ItemPushArea
```

## 2. 文件组织与基类选择

不同职责的脚本用不同基类，按下面的对应关系选择：

| 用途 | 基类 | 例子 |
|---|---|---|
| 玩家/敌人等有物理行为的角色 | `CharacterBody2D` | `RealtimePlayer.gd`、`BasicEnemy.gd`、`BulletHellEnemy.gd` |
| 玩家子系统（战斗/技能/交互/推挤等逻辑对象，不上场景树） | `RefCounted` | `PlayerCombatController.gd`、`PlayerSkillController.gd` |
| 纯数据/状态容器（不挂节点，或作为逻辑单例节点使用） | `RefCounted` 或 `Node`（视是否要挂树） | `RunProgressionState.gd`（RefCounted）、`LevelContext.gd`（RefCounted） |
| 管理器/控制器类节点 | `Node` | `OrderManager.gd`、`BattleManager.gd`、`StorageManager.gd`、`LevelFlowController.gd` |
| 全屏UI/HUD | `CanvasLayer` 或 `Control` | `OrderHud.gd`（CanvasLayer）、`GameStartController.gd`（Control） |
| 场景内可交互设施 | `StaticBody2D`，需要编辑器内预览效果时加 `@tool` | `AssemblyStation.gd` |

场景与脚本基本一一对应（`AssemblyStation.tscn` <-> `AssemblyStation.gd`），但纯代码构建UI（如 `GameStartController.gd` 用大量 `Button.new()`/`VBoxContainer.new()`）和运行时动态创建的纯视觉节点（如 `PlayerBuffIndicator` 用 `.new()` 创建后 `add_child`，没有对应 `.tscn`）是允许的模式，不是必须都要有场景文件。

## 3. 代码风格

### 缩进

Tab，不用空格。

### 脚本内部分区顺序

项目里没有用 `#region`/`#endregion` 或分类标题注释来分区，而是靠**固定的代码块顺序**隐性分组，新脚本按这个顺序写：

1. `extends` / `class_name`
2. `const XXX = preload(...)` 依赖声明
3. `signal` 声明
4. `@export` 变量（用命名前缀分组，例如 `attack_*`、`dash_*`、`item_push_*`，不加注释分隔）
5. `@onready` 节点引用
6. 普通 `var` 运行时状态
7. 生命周期函数：`_ready` / `_process` / `_physics_process` / `_input`
8. 公共接口方法
9. `_` 前缀私有辅助方法

### @export 用法

- 能调的数值尽量都 `@export` 出来，方便在编辑器里调参（`RealtimePlayer.gd` 一个文件里有60+个）。
- 靠命名前缀分组，不用注释分隔小节。
- 需要限制范围时用 `@export_range`：`@export_range(0.0, 1.0, 0.05) var facility_preview_tint_strength: float = 0.8`。
- 默认值显式给出，包括 `Color`/`Vector2` 这类复合类型，不留空。

### 类型标注

**严格标注，这是全项目最一致的硬约定**，新代码必须遵守：

```gdscript
func try_attack(aim_direction: Vector2, can_damage_target_across_zones: Callable) -> bool:
func get_current_attack_damage() -> int:
var current_health: int = 0
```

- 函数参数、返回值（包括 `-> void:`）、变量声明都写类型。
- 容器类型进一步标注元素类型：`Array[Dictionary]`、`Array[String]`、`Array[NodePath]`。

## 4. 注释

- 没有文件头注释（版权/作者/日期块），脚本直接从 `extends`/`class_name` 开始。
- 函数级注释很少，靠命名自解释。有注释的地方一般是解释“为什么这么写”而不是“这段代码做什么”，用英文，例如：

```gdscript
# Tab is also used by Godot's UI focus system, so keep a narrow fallback for
# the prototype when the action mapping does not surface as a normal press.
```

- **代码注释（`#`）用英文，玩家可见的字符串字面量（UI文案、提示语、数据表里的显示名）用中文**。这是项目的固定分工，不要混用反过来（比如不要给内部逻辑注释写中文，也不要给玩家UI文案写英文占位后不补中文）。
- 中文字符串的修改必须遵守 `Docs/文本与场景修改硬约束.md` 里的规则（见 `CLAUDE.md` 摘要或该文档原文），核心是：一旦发现乱码不要局部补丁，整段/整文件重写，改完后跑 headless 校验。

## 5. 数据定义类的写法

游戏数据（食材、菜品、订单组、祝福等）现状是 `RefCounted + class_name`，用 `static func` 返回字面量表，不是 Godot `Resource`/`.tres`：

```gdscript
class_name OrderGroupDefs
extends RefCounted

static func create_default_order_groups() -> Array[Dictionary]:
    return [_build_wave(...), ...]

static func _build_wave(...) -> Dictionary:
    ...
```

或者用平行的 `const Dictionary` 做表驱动（`TestItemDefs.gd` 的写法）：

```gdscript
const ITEM_DISPLAY_NAMES: Dictionary = {...}
const ITEM_TEXTURES: Dictionary = {...}
const RECIPES: Dictionary = {...}
```

新增游戏数据时跟随这个模式，不要引入 `Resource`/`.tres` 方案，除非项目里已经决定要迁移（目前没有）。

## 6. 命名里容易踩坑的地方

- `Test*` 前缀（`TestTable.gd`、`TestCooker.gd`、`TestItemDefs.gd`、`TestServingCounter.gd`）表示“原型阶段占位实现”，**不是单元测试**。项目里没有任何单元测试框架，看到 `Test` 开头不要以为是可以随意删除的测试代码——尤其 `TestItemDefs.gd` 是被广泛 `preload` 的核心数据表。已删除的防御塔原型不再属于当前脚本集合。
- 新脚本如果概念上取代了某个 `Test*` 脚本，建议直接用无 `Test` 前缀的正式名字，避免继续扩大这个命名歧义（例如未来要重构料理台系统，正式版命名为 `Cooker.gd` 而不是继续叫 `TestCooker2.gd`）。
