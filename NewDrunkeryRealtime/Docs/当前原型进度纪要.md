### 0.6 本次补充更新：夜晚区域挡路、拆分复查与当前执行顺序

这次对话又补充确认了三件重要的事。

第一，夜晚区域前出现的“巨大空气墙”已经定位并修复。

- 问题本质不是场景里真的多了一堵墙。
- 真正原因是玩家移动边界仍停留在旧默认值 `Rect2(0,0,1792,1152)`，而商人 / 任务书位于更靠下的夜晚区域。
- 结果就是玩家在接近夜晚区块时，会像撞到 invisible wall 一样被硬裁掉。

当前修复方式：

- `RealtimePlayer.gd` 不再只依赖固定父节点结构去拿 `PrototypeMap`。
- 玩家移动边界会主动从 `PrototypeMap.get_world_bounds()` 同步。
- `PlayerPushController.gd` 已补上可更新 movement bounds 的入口。

当前判断：

- 这是一次典型的“拆分后保留旧默认值，导致运行范围和场景尺寸脱节”的问题。
- 该问题已经修掉，后续地图尺寸再变化时，玩家边界不应再次凭空形成空气墙。

第二，已经对今天拆分出的控制器和主脚本做过一轮针对性复查，并修掉了一处真实的接线遗漏。

复查范围包括：

- `LevelFlowController.gd`
- `RunSetupController.gd`
- `RunOverlayController.gd`
- `RealtimePlayer.gd`
- `PlayerInteractionController.gd`
- `PlayerCombatController.gd`
- `PlayerPushController.gd`

这轮复查确认：

- 当前拆分后的职责边界整体仍然成立，没有发现新的致命流程 bug。
- 但 `NightShopController` 在拆分后确实存在“创建时机晚于场景引用注入”的接线遗漏风险。

当前已修复：

- `LevelFlowController.gd` 已补上统一的运行时 controller 引用回填逻辑。
- `NightShopController` 创建完成后，会重新拿到 `player / defense_tower / storage_manager`。

当前结论：

- 今天的拆分结果已经达到“可继续开发”的程度。
- 现阶段没有必要因为担心潜在问题而回滚拆分。
- 真正需要继续警惕的是：以后若再拆控制器，必须同步检查“创建顺序”和“场景引用注入顺序”。

第三，这次对话已经明确当前更合适的执行顺序：

- 先测试功能，再修改文本与乱码。

原因不是中文化不重要，而是：

- 当前项目里“功能问题”和“编码 / 文本问题”如果混在同一轮处理，容易互相制造噪音。
- 先把功能链路跑通、确认行为，再集中处理中文显示和文本一致性，会更稳。

因此，当前默认策略改为：

1. 优先保证功能可用、可测
2. 功能确认后，再集中处理中文显示、乱码和文本统一
3. 不在同一轮里频繁来回穿插“修功能”和“修文本”

补充说明：

- 这不等于忽略乱码问题，只是把它从“开发中实时打断处理”改成“功能确认后的集中清理项”。
- 本节优先级高于文档后文仍保留的旧开发顺序描述；若后文有冲突，以本节为准。

## 1. 项目定位

- 当前项目是一个独立的 Godot 即时制原型工程。
- 它不再沿用旧版本“回合制卡牌 + 战棋 + 经营”的主架构。
- 当前验证方向是：
  - 即时制战斗
  - 食材获取
  - 半成品加工
  - 菜品组合
  - 订单与上菜
  - 经营压力与战斗压力并行

当前目标不是补完所有系统，而是先把“战斗获取食材 -> 加工 -> 组合 -> 接单 -> 上菜”这条主循环跑通。

## 2. 当前操作方案

当前原型内的核心输入为：

- `WASD`：移动
- 移动方向：决定玩家朝向与交互方向
- `SPACE`：冲刺
- `J`：拿起 / 放下 / 放到桌上 / 从桌上取回 / 上菜 / 从仓库拿取 / 放回仓库
- `K`：与主动设施交互
- `L`：自动瞄准最近可命中敌人并普通攻击
- `U`：小技能
- `I`：大招
- `TAB`：展开 / 收起订单

当前额外已接入的 UI / 夜晚输入为：

- `A/D` 或方向键：在订单选择卡 / 祝福卡之间切换
- 鼠标悬停：切换当前高亮卡片
- 鼠标左键：直接确认当前订单组 / 祝福
- `Esc`：从任务书订单选择界面返回夜晚

当前夜晚商店输入已扩展为：

- `J/K`：切换商店分类页
- `ui_confirm`：购买当前选中商店项
- 鼠标悬停：高亮当前商店项 / 任务书卡片
- 鼠标左键：直接购买商店项 / 直接确认订单组
- 鼠标滚轮：滚动商店商品区

当前交互逻辑共识：

- 玩家朝向跟随最近一次移动方向，不再依赖鼠标。
- 玩家前方存在一个扇形交互区域。
- 只有处于交互区域内，并且朝向判定合格的对象才会被选中。
- 当前方案允许“即使按 `J` / `K` 实际不会有反应，也依然显示高亮”，用来告诉玩家该设施是可交互对象。

## 6. 当前明确的设计共识

### 6.1 菜品结构

- 所有菜品都应由多个“处理过的食材 / 半成品”组合而成
- 不走“单一食材直接变成完整菜品”的长期路线
- 当前测试菜品只是为了验证链路，不代表最终设计方向

### 6.2 组合逻辑

- 不采用“盘子即组合核心”的默认做菜游戏方案
- 当前更倾向于保留“组合台”作为明确设施
- 理由是组合台更方便承载之后更复杂、更有趣的机制设计

### 6.3 地图与资源流向

- 当前原型恢复为“战斗区 + 料理区”两段式地图
- 肉类资源开始转向由战斗区提供
- 玩家不需要把敌人掉落一个个搬回后厨，接触后自动入仓
- 料理区 loose item 与战斗区 battle drop 必须长期保持两套交互逻辑：
  - 料理区：`J` + 交互扇形
  - 战斗区：身体接触自动入仓

### 6.4 订单状态的职责划分

- 订单数据与状态不应继续完全绑在 HUD 上
- HUD 负责显示
- `OrderManager` 负责订单实例、完成、超时与波次内活跃状态

### 6.5 输入与可用性

- 当前阶段优先保证可玩、可测
- 某些输入或订单逻辑允许采用“原型期稳定方案”
- 等正式系统成型后，再统一做结构整理
- 当前夜晚 / 订单选择 / 祝福选择已统一到 action 驱动的 UI 输入层
- `A/D`、方向键、确认键、鼠标悬停 / 点击都已经接入统一 UI 选择流程
- 夜晚商店当前处于“输入方案仍在调整但功能已接通”的阶段：
  - 分类切换已经支持 `J/K`
  - 鼠标悬停高亮已经重新接通
  - 商店卡片式 UI 最近刚做过一轮缩放与布局调整
  - 这部分当前最需要的是系统化实机测试，而不是继续盲改

### 6.6 当前战斗开发顺序

- 当前优先开发“机制型敌人”，而不是先做数值平衡
- 敌人差异重点放在：
  - 预警表现
  - 攻击形态

  - 区域压制方式
- 等敌人攻击种类足够丰富后，再回头统一讨论节奏与数值

当前结论：

- 结构性死递归入口已被封堵。

## 11. 下次对话最应该优先做的事
