## 1. 项目当前方向

项目是 Godot 4.7 制作的即时制独立游戏原型，核心体验从旧版“回合制卡牌 + 战棋 + 经营”转为：

`多人协作料理 + 即时战斗采集 + 肉鸽构筑成长`

当前希望验证的核心乐趣是：

- 玩家在料理区处理订单、备菜、上菜。
- 玩家进入战斗区打怪或采集资源，为厨房提供食材。
- 夜晚进行菜单调整、厨房摆放、商店购买和次日关卡选择。
- 单人能忙而不乱，多人能自然分工。

当前阶段不建议继续添加大系统。下一阶段应优先打磨“首日完整体验”，让玩家第一天就能清楚知道：今天菜单是什么、需要哪些食材、需要哪些料理台、哪里接单、哪里上菜、哪里采集、什么时候该去战斗区。

## 3. 代码架构约定

项目没有使用 autoload / 全局单例。跨场景一次性传递数据使用 `SceneTree.set_meta()` / `get_meta()`。

`LevelRefs.gd` 是场景内服务定位器，不是 autoload。新增系统级节点引用时，优先接入 `LevelRefs`，不要到处硬编码父子路径。

玩家逻辑使用 `RealtimePlayer.gd` + 多个 `RefCounted` Controller 组合：

- `PlayerInteractionController.gd`
- `PlayerCombatController.gd`
- `PlayerSkillController.gd`
- `PlayerPushController.gd`

关卡流程使用：

- `LevelFlowController.gd`：主流程、夜晚 / 白天状态、菜单 / 商店 / 关卡选择、魔力。
- `RunSetupController.gd`：重置玩家、仓库、料理台、初始化库存。
- `RunOverlayController.gd`：全屏 UI / 结算 / 夜晚界面承载。
- `RunProgressionState.gd`：跨天长期状态，包括金币、经验、等级、天数、当前菜单、待选菜单。
- `LevelContext.gd`：单日运行时状态，包括当前关卡、波次、声望、订单进度。

数据仍主要写在硬编码字典表里：

- `TestItemDefs.gd`：食材、菜品、配方、图标、显示名、收益。
- `OrderGroupDefs.gd`：关卡 / 波次 / 订单组。
- `BlessingDefs.gd`：祝福。

不要未经讨论把这些整体迁移成 `.tres` / Resource。

## 4. 当前已经实现的主要内容

标题与开局：

- 已有标题界面和开局选择界面。
- 当前只开放一个角色，其他角色作为占位。
- 可以选择小技能、大招、初始遗物，但部分效果仍偏占位。
- 主界面有图鉴入口。

主循环：

- 夜晚休整。
- 组合台承担菜单查看 / 菜单调整 / 开始营业 / 选择关卡入口。
- 第一天关卡选择只有一个选项，后续天数可出现选择。
- 白天有准备期、订单波次、波间休整、结算。
- 完成订单获得金币和经验，失败扣声望。
- 声望过低会进入危险倒计时。

菜单系统：

- 当前菜单保存在 `RunProgressionState.menu_dish_ids`。
- 初始菜单只有一道菜。
- 达到指定天数时必须先更新菜单，之后才能开始下一天。
- 菜单上限当前为 4，道菜满后走替换而不是无限增加。
- 关卡订单会基于当前菜单重写，不再直接固定为关卡原始菜品。

料理与食材：

- 当前有 12 种食材，包含肉类与非肉类。
- 沙漠地区食材包括红鬃羊肉、沙原禽肉、沙兔肉、脆脆芽、风铃椰、旱霜白菜、晴天梅、沙薯、砂冠花、莳萝、碎金子、太阳籽。
- 当前仍保留大量旧料理台加工状态：切、蒸、炒、炸、煮、烤。
- 当前菜品数据较多，但即将重做为更少料理台、更清晰分类的结构。

饮料系统：

- 已有酒桶和饮料物品。
- 当前酒桶仍是手动按键读条补充，开局库存为 0。
- 当前有两类基础酒水：绿洲葡酒、椰枣麦酒。
- 当前有扩展饮品 / 酒水入菜的测试菜品。
- 最近设计共识是：酒桶应改为自动慢速补水，不再需要玩家手动补水。

战斗：

- 玩家有轻攻击 / 重攻击蓄力 / 冲刺。
- 轻攻击有更强自动索敌，避免玩家频繁“摇头”。
- 重攻击松手瞬间立即确定实际生效范围，视觉跟随该范围，避免动画打到但不掉血。
- 重攻击可作为功能性攻击，未来会和敌人前摇打断 / 破防联动继续深化。
- 基础攻击加入了很短的冷却，防止玩家快速连按秒杀敌人。

敌人与战斗区：

- 当前有多个敌人原型，包括近战、冲刺、砸地、远程、弹幕、分裂 / 环绕等。
- 战斗区分为多个小地区，地区之间用沙丘墙隔开，每段连接只保留两格宽入口。
- 敌人应固定属于自己的战斗区，不应跑到非所属区域。
- 最近已经去掉“不靠近边缘 20%”的设计倾向，只需要保证不离开所属战斗区。
- 最近修复过玩家在料理区右下角向下冲刺被夹取到第一个战斗区并卡进沙丘的问题。

采集：

- 非肉类食材来自战斗区内随时间刷新出的采集小点。
- 采集点白天刷新，夜晚不刷新。
- 每个采集区域有固定产物池。
- 玩家靠近按键进入搜索状态，结束后出现若干按键选择，位置随机。
- 成功或失败后采集点都会消失。
- 采集结果直接入仓，不让玩家手拿食材跑回厨房。

料理区与摆放：

- 料理区目前是规则矩形，战斗区在上方形成类似蘑菇伞结构。
- 固定上菜口从多个方向包围料理区。
- 固定酒桶存在于餐厅上方，作为阻挡和饮料来源。
- 组合台固定在中心位置，不可移动。
- 桌子不会自行移动，但可以被玩家搬动。
- 食材仓库可以搬动。
- 料理台是“活物”，白天会自行移动。
- 玩家可用魔力 Block 活动料理台，使其暂时停住。
- Block 后可以搬起料理台调整位置。
- 搬运料理台时玩家减速、不能冲刺、不能做其他交互。
- 料理台被完全围住时，结束 Block 后会生气，把四周阻挡物击飞到随机空格。

魔力：

- 魔力显示在声望附近，是蓝色竖条并带分格。
- 魔力会缓慢恢复。
- Block 料理台需要魔力。
- 搬动被 Block 的料理台时，一格内免费，超过距离按格消耗魔力。
- 搬起料理台时 Block 倒计时暂停。
- 夜晚允许自由摆放；白天开始会给料理台一段免费 Block 时间，但后续调整仍消耗魔力。

商店与支援设施：

- 夜晚商店已接入购买逻辑。
- 当前初始金币已提高到 120，方便测试店内设施。
- 商店分类用 `Q/E` 切换，方向键 / WASD 选择商品，`Space` 购买，`K` 关闭，鼠标与滚轮也可用。
- 已有可购买支援设施：履带、台灯、水壶。
- 履带是二格传送带，放下后沿箭头方向推动玩家和散落物；搬在手上时按 `L` 切换方向。
- 台灯提升附近料理台加工速度。
- 水壶提升附近酒桶填充速度。

上菜与订单：

- 客人来到上菜口后，先显示点单提示。
- 玩家到对应上菜口交互后才正式生成订单倒计时。
- 点单前不显示客人要吃什么。
- 点单完成后，上菜口旁显示倒计时，不在上菜口上直接显示菜品。
- 顶部订单 HUD 显示已接订单和配方信息。
- `TAB` 可展开 / 收起订单 HUD。

交互提示：

- 凡是可交互对象，玩家靠近后会渲染对应按键提示。
- 提示不需要写“切菜 / 点餐 / 采集”等动作文字，只显示按键。
- 风格希望像灰色像素风键盘键帽。

## 5. 近期关键设计共识

第一地区是沙漠地区，文化参考方向是中东 / 古埃及。敌人暂时不用完全重做，但食材和菜品应更贴合地区气质，减少水产感。

料理台设计即将重做。当前共识是：不要在一张地图中塞入太多料理台。每个地区只放少数几种料理台，让学习成本下降；菜品复杂度主要来自半成品数量、加工链条、菜单规划和组合台小游戏，而不是靠六种料理台同时上场。

最新讨论明确为：

`三种料理台 + 一个独立组合台`

组合台不算料理台。组合台承担最终组装、菜单查看、菜单调整、开始营业、关卡选择，以及主菜 / 甜品的组合小游戏。

菜品建议分为四类：

- 酒水：可以直接上菜。
- 小菜：需要组合台，但不玩小游戏。
- 主菜：需要组合台小游戏。
- 甜品：需要组合台小游戏。

“料理”这个分类太宽泛，建议玩家可见分类叫“主菜”。

候选三种料理台方向：

- 处理台：类似原本切菜，多次点击，稳定不失败，承担基础备菜。
- 火候台：自动加工，有最佳取出窗口，放太久会糊，承担时间管理压力。
- 第三台尚未最终确定。之前提出的“冷调台：顺序/配比选择”被认为过于麻烦，不适合作为单独小玩法，最多可作为组合台高级菜品玩法。更适合考虑一种低学习成本但节奏不同的台，例如炖煮台 / 压制台 / 晾晒台 / 研磨台。

## 6. 当前明确需要重做或调整的内容

酒桶系统：

- 改成自动补水 / 自动酿造。
- 开局不自带层数。
- 每次读条完成后只获得一杯量。
- 补水 / 酿造所需时间大幅提高。
- 玩家只负责取酒水，不再负责手动补水。
- 水壶仍可作为提高附近酒桶填充速度的支援设施。

料理台与菜单：

- 从“六种料理台并存”改为“每张地图只使用三种料理台”。
- 第一地区菜单需要整体重做，围绕三种料理台和四类菜品重新规划。
- 当前 `TestItemDefs.gd` 中的菜品与配方是旧结构，需要迁移。
- 旧的蒸、炒、炸、煮、烤状态不一定全部保留在第一地区。
- 需要先确定第三种料理台的交互方式，再批量重做菜品。

首日体验：

- 第一日应只让玩家接触 1-2 道菜。
- 食材箱只显示当前菜单需要的食材。
- 料理台只显示当前菜单需要的台。
- 菜单调整必须是阶段性行为，不应让玩家开局看到所有菜。
- 组合台夜间需要能清楚查看当前菜单与每道菜做法。

订单 HUD：

- 顶部订单 HUD 目前经过多轮修正，但仍需要继续手测。
- 重点确认图标大小、配方可读性、展开 / 收起状态、窗口缩放后的显示位置。
- 订单 UI 不应遮挡玩家看游戏画面。

移动料理台：

- 活动料理台仍需要继续测试卡位问题。
- 它们应有碰撞体积并避免相互重叠。
- 被 Block 时倒计时条应明显显示在料理台底部。
- 玩家靠太近 Block 后，料理台应自动吸附到最近格子，并把玩家顶开到安全格。

防御塔：

- 设计上已经决定删除防御塔系统，不再作为当前核心方向继续开发。
- 代码和资源里可能仍存在 `TestDefenseTower` 等遗留文件或引用，需要后续清理。
- 现在单人保底更倾向通过敌人 / 采集 / 菜单节奏 / 祝福和设施来调，而不是固定防御塔。

图鉴：

- 图鉴已存在，但应持续确保敌人、食材、料理、料理台都有图片。
- 列表滚动、高亮同步、文字边距和图标辨识度已经修过，但后续换新菜单后需要更新内容。

## 7. 建议下一阶段开发顺序

第一优先级：冻结大系统，打磨首日闭环。

- 第一日只保留必要菜单、必要食材、必要料理台。
- 让组合台夜间菜单页足够清楚。
- 让玩家知道需要准备什么半成品。
- 确保接单、做菜、采集、上菜没有明显卡点。

第二优先级：重做第一地区料理结构。

- 先确定第一地区的三种料理台。
- 再定义四类菜品的复杂度规则。
- 再重写 `TestItemDefs.gd` 的菜品和配方。
- 最后同步 `OrderGroupDefs.gd` 的订单组。

第三优先级：酒桶自动化改造。

- 先把酒桶改为自动产出。
- 再增加更长产出时间和每次一杯。
- 最后测试饮料订单是否自然形成“提前规划”而不是高频补水。

第四优先级：活动料理台与摆放手感回归。

- 测试白天料理台移动是否制造趣味，而不是烦躁。
- 测试 Block 成本、持续时间、免费距离、魔力恢复。
- 测试玩家是否会通过箱子 / 桌子 / 设施自然构建厨房空间。

第五优先级：清理旧系统遗留。

- 清理或隔离防御塔遗留引用。
- 删除不再使用的旧料理台场景或先隐藏。
- 减少第一地区不需要出现的料理台和菜品。

第六优先级：内容扩充。

- 在首日好玩以后，再补祝福池、商店内容、非料理设施、敌人联动。
- 不建议现在继续直接加新系统。

## 9. 当前最值得立刻讨论的问题

第三种料理台到底是什么。

已排除方向：

- 单独的冷调台不合适，因为“选择 / 配比 / 顺序”太像组合台高级小游戏，会增加学习成本。

可继续讨论的方向：

- 炖煮台：长读条、宽窗口、不容易失败，适合汤、炖肉、甜粥。
- 研磨台：短读条、多次投入，适合碎金子、莳萝、太阳籽，能支撑酱料 / 粉 / 油。
- 晾晒台：放置后等待，无糊锅但占空间，适合沙漠主题，能和移动料理台形成空间压力。
- 压制台：按住蓄力到区间，松手完成，适合饼、肉排、甜品坯，但可能和战斗蓄力手感重复。

我的当前倾向：

`处理台 + 火候台 + 研磨/压制混合台`

原因是它能保留沙漠地区的谷物、香料、太阳籽特色，也能让小菜、主菜、甜品拥有不同半成品来源，同时不会像冷调台那样要求玩家在普通料理台上做复杂决策。

## 10. 一句话总结

当前项目已经拥有相当完整的原型骨架，但内容层正处在一次必要的收束点：不要再堆更多系统，而是把第一地区改造成低学习成本、高可读性、能支撑首日体验的版本，再逐步扩展料理台、菜品、祝福、商店和敌人联动。
